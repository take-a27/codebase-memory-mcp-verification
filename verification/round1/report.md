# ラウンド 1：公式の入れ方で、使うかどうかは Claude に任せる

2026-11-08 / Claude Code 2.1.319 + Opus 5.5 / codebase-memory-mcp v0.12.1 / Kubernetes v1.37.2
ラウンド 2（CLAUDE.md で使うよう指示）のレポート：[../round2/report.md](../round2/report.md)

## 条件

- **MCP あり（B）は、公式の入れ方。** 公式インストーラーが入れるもの（MCP・スキル・エージェント 3 つ・hooks）を、すべて有効にした。hooks は、セッション開始時の案内と、grep / Read のたびにグラフの情報を添える補助。「MCP を使って」という指示はどこにも足していない。
  - 普段の `~/.claude` を汚さないよう、インストーラーは偽の HOME に対して実行した。入ったものは `--mcp-config` / `--settings` / `--plugin-dir` で B の実行時だけ読み込んだ（[setup_official.sh](../scripts/setup_official.sh)）。
  - hooks のグラフ補助に必要なデーモンも起動した。
- **MCP なし（A）は、素の Claude Code。** ユーザーのプラグインと hooks は読み込まないが、組み込みのスキルは有効。
- **お題は 6 つ。** 実際の開発で頼みそうなもの。T4〜T6 はグラフが得意そうなものを選び、正解はソースから機械的に抽出した（[ground_truth.md](ground_truth.md)）。
  - T1 **関数の使われ方**：「`podutil.IsPodReady` の呼び出し元と、何に使われているかを調べて」
  - T2 **リファクタ候補**：「`pkg/controller` で重複している処理を探して、まとめ方を提案して」
  - T3 **処理の流れ**：「Pod が作られてから、スケジューラーがノードにバインドするまでの流れを説明して」
  - T4 **影響範囲**：「`IsPodAvailable` に引数を追加したい。修正が必要な呼び出し元と、波及しそうな箇所を洗い出して」
  - T5 **未使用コード**：「`pkg/controller` で、もう使われていない関数を探して、削除してよさそうな候補を根拠付きで挙げて」
  - T6 **インターフェースの実装一覧**：「新しい Filter プラグインを追加したい。既存の Filter プラグインを全部挙げて、それぞれ何をチェックしているか説明して」
- **採点**は、条件を伏せたうえで `claude -p`（Opus 5.5、読み取り専用）がソースで裏取りしながら 1〜5 点をつけた。

## 結論 3 行

1. **ちゃんと入れても、Opus は 18 回中 15 回、MCP を一度も呼ばなかった。** 呼んだのは「未使用の関数」を聞いた T5 だけ。スキルの説明（いつ使うかの一覧）には、T1〜T5 に当たる言葉（who calls this function、refactor candidates、trace the call chain、impact analysis、dead code）がすべて並んでいる。それでもスキルが起動したのは T5 だけで、それ以外は grep で済ませた。
2. **使わないときは、ほぼ「上乗せ」だけになる。** スキルやエージェントの一覧、案内文で、1 リクエストあたり約 1,700 トークンが毎回増える（16,661 → 18,366）。そのため総トークンは 6〜31% 増え、時間と質はほぼ変わらなかった。
3. **使ったとき（T5）は 3.3 倍速くなったが、取りこぼしが出た。** 時間は 351 秒 → 105 秒。MCP なしは grep をループで何百回も回していて、手元での実行時間が長かった。一方、グラフのクエリは「関数」に絞られていて、メソッド（`ByLogging` など）の未使用を見落とした。質は 5.0 → 4.0、トークンは 2.2 倍だった。

## 何が起きていたか

### MCP を使わなかった 15 回
- セッション開始時の hook は「インデックスは作成済み、まず scout で調べて」と案内していた。それでも Opus は自分の判断で grep を選んだ。
- grep の hook は、グラフから見つかった同名シンボルの一覧を毎回裏で添えている（[動作を確認済み](#補足hooks-の動作確認)）。ただ、これで答えの質が上がった様子はない。
- その結果、MCP ありは「固定の上乗せ（約 1,700 トークン × ターン数）＋ hook の補助情報」の分だけ重くなった。

### MCP を使った T5
- 3 回ともスキル（`codebase-memory`）が起動し、`query_graph` で「呼び出しが 1 件もない関数」を一気に抽出した。そのあと grep で裏取りしていた。
- **速かった理由**：MCP なしは、関数名ごとに `git grep` をループで回していた。MCP なしの API 時間は 90〜111 秒だったのに、経過時間は 233〜466 秒あり、差の大半は手元での grep の実行時間だった。MCP ありの経過時間は 91〜119 秒。
- **質が下がった理由**：クエリが「関数」ノードに絞られていて、メソッド（`ByLogging` など）が抜けた。採点者は、テストからだけ使われる関数の区別が弱い点も指摘している。MCP なしは時間をかけてメソッドまで調べ、3 回とも満点だった。
- **両条件とも見つけたもの**：`protectionutil.MakePod` は、別パッケージの同名関数（`st.MakePod`）が大量に使われているせいで、単純な grep では「使われている」ように見える（私が作った正解リストからも漏れていた）。それでも両条件とも 3 回すべてで、これを未使用として見つけていた。`IsValidMode` と `daemon.NewPod` も両条件とも全回で挙げている。差がついたのは `ByLogging` などのメソッドで、MCP なしは 3 回とも挙げ、MCP ありは 0 回だった。

### T4 と T6（グラフが得意そうなお題）でも MCP は使われなかった
- 「呼び出し元を洗い出して」「インターフェースの実装を全部挙げて」は、グラフの得意分野のはず。それでも Opus は grep 1〜2 回で正解のほぼ全部にたどり着いた。そのため MCP を呼ぶ動機がなかった。
- T4 の減点は、両条件とも「件数の数え間違い」が中心だった。

## 結論

- **使うかどうかを任せると、ほとんど使われず、上乗せのコストだけが残った。** Opus + Claude Code で、Kubernetes の調査を新しいセッションで 1 問ずつ頼む使い方では、入れるメリットはほぼなかった。
- **はっきり効いたのは「リポジトリ全体を総当たりで調べる」質問（T5 の未使用コード）の速さ。** grep を何百回も回すような調査では、グラフのクエリ 1 回のほうが圧倒的に速い。ただし、クエリの範囲次第で取りこぼすので、結果の裏取りは必要。
- では、使うよう指示したらどうなるか。それを確かめたのが [ラウンド 2](../round2/report.md)。

## 注意点・限界

- 各条件 3 回だけ。モデルは Opus 5.5 だけ。新しいセッションでの初回の質問だけを測っている。
- 最初の 1 回（T1-B-1）は、デーモンを起動する前に実行していた。そのため、セッション開始時の案内と grep の補助が入っていない。残りの 17 回はデーモンありで実行していて、T1 の残り 2 回も MCP を使っていないので、結論は変わらない。
- 採点は LLM（Opus 5.5）が 1 回だけ。T5 の「調べ方」の記述には、条件を推測できる言葉（`[tool]上は…` など）が残っていた。
- T5 の正解リストは、トップレベルの exported 関数しか機械的に抽出していない（メソッドや型、同名の別関数がある場合は対象外）。採点では「ソースで確認できる妥当な指摘は加点」として扱った。
- コストはサブスクリプションでの API 料金換算の参考値。
- `pkg/controller` の未使用関数のように、Kubernetes は lint で未使用コードを取り除いているので、もともと答えが少ないお題になっている。
