## 条件

- **MCP あり（B）は、ラウンド 1 の B と同じ公式の入れ方（MCP・スキル・エージェント・hooks）に、CLAUDE.md を 1 つ足しただけ。** Kubernetes のルートに次の [CLAUDE.md](CLAUDE.md) を置いた。実際に「使ってほしい」ときに書きそうな内容にした。
  > コードの構造を調べるとき（関数の呼び出し元・呼び出し先、処理の流れ、変更の影響範囲、未使用コード、インターフェースの実装の一覧など）は、grep より先に codebase-memory-mcp の MCP ツール（search_graph、trace_path、query_graph、get_code_snippet など）を使うこと。文字列や設定ファイルを探すとき、グラフの結果を裏取りするときは、grep や Read を使ってよい。
- **MCP なし（A）は、ラウンド 1 の A と同じ条件なので、ログを使い回した。**
- **お題（T1〜T6）と採点観点もラウンド 1 と同じ。** 採点は、A と B の回答を混ぜて、改めて条件を伏せて行った（`claude -p`、Opus 5.5、ソースで裏取り）。そのため A の質の点はラウンド 1 と少し違う（同じ回答でも採点のたびにぶれる）。

## 結論 3 行

1. **指示すれば、18 回中 18 回 MCP を使った。** ラウンド 1（任せる）では 18 回中 3 回だった。CLAUDE.md の指示はちゃんと効く。
2. **それでも、速くも安くもならなかった。** 総トークンは 1.79 倍、コストは 1.34 倍。時間は T5（未使用コード）だけ 351 秒 → 157 秒と速くなったが、それ以外は 1.1〜1.3 倍遅くなった。18 回すべてで、グラフを見たあとに結局 grep や Read でコードを読みに行っていて、そのぶん手数が増えた。
3. **質はむしろ下がった（4.22 → 3.89）。** 特にリファクタ候補（T2）は 3.67 → 2.33。グラフで「同じ名前の関数が複数あるもの」を探すやり方に引っ張られたうえ、そのクエリがメソッドを対象にしていなかったので、ワーカーループのような「形が同じ処理」の重複を見落とした。

## 何が起きていたか

### 毎回「グラフ → 結局 grep / Read」
18 回とも、最初に ToolSearch で MCP ツールを読み込み、グラフに問い合わせてから、grep や Read でコードを読んでいた。グラフだけで答えた回はない。たとえば T1 はこうなる。

```
MCP なし（T1-A-1）: Bash(grep) → Bash → Bash                         … 3 手、32 秒
MCP あり（T1-B-2）: ToolSearch → search_graph → trace_path → get_code_snippet
                    → Bash × 4                                       … 8 手、48 秒
```

Claude Code はやりとりのたびに会話全体を読み直すので、手数が増えるとトークンもそのぶん増える。グラフは grep や Read の「代わり」にはならず、「前に挟まる 1 ステップ」になった。

### T2 の質が下がった理由：グラフ向きの問いに言い換えてしまう
MCP ありは 3 回とも、`query_graph` で「`pkg/controller` の中で同じ名前の関数が複数あるもの」を探すところから始めた（`MATCH (f:Function) ... WITH f.name AS name, count(*) AS c ... WHERE c > 1`）。このクエリは `Function` ノードだけが対象で、`Method` は入らない。ワーカーループの `processNextWorkItem` や `worker` はコントローラーのメソッドなので、最初から候補に出てこない。T5 でメソッドの未使用を見落としたのと同じ形の取りこぼし。その結果、`uidCache`、`printDiff`、`usagesToSet` のような**同名の小さな関数の重複**は正確に挙げた。一方で、正解の要点だった**ワーカーループやイベントハンドラーのような「形が同じ処理」の重複**は、ほぼ挙げなかった。MCP なしは grep で `processNextWorkItem` や `resolveControllerRef` を数えて、そちらを中心に答えていた。

### T3 と T4 も少し下がった
- T3：MCP ありは 3 回とも、スケジューラー側は正確だったが、API サーバーで Pod を作成する部分（`strategy.go`）が抜けた。
- T4：両条件とも件数の数え間違いが中心。MCP ありは、数え間違いに加えて関数の対応の取り違えもあった。

### T5 は速くなった（ラウンド 1 と同じ傾向）
- 時間は 351 秒 → 157 秒。MCP なしは関数名ごとに grep をループで回すので、手元での実行に時間がかかる。グラフなら「呼び出しが 0 件の関数」をクエリで出せる。
- ただし、メソッドの未使用（`ByLogging` など）は、ラウンド 1 と同じく 3 回とも見落とした。今回の採点では、MCP なしの回答も「テストからだけ使われている関数」の具体名がない点で減点されたため、質の点は MCP ありのほうがわずかに高くなった。

### T1 の別名 import
`disruption.go:931` は、`apipod` という別名で import して `IsPodReady` を呼んでいる。MCP ありは 3 回とも別名まで説明していた。ただ、MCP なしも 3 回とも `disruption.go:931` を挙げていたので、差はつかなかった。

## ラウンド 1 と合わせた結論

| | ラウンド 1（任せる） | ラウンド 2（CLAUDE.md で指示） |
|---|---|---|
| MCP を使った回数 | 18 回中 3 回 | 18 回中 18 回 |
| 総トークン（MCP なし比） | 1.56 倍 | 1.79 倍 |
| コスト（MCP なし比） | 1.21 倍 | 1.34 倍 |
| 時間（T5 を除く） | 750 秒 / 722 秒（1.04 倍） | 858 秒 / 722 秒（1.19 倍） |
| T5 の時間 | 351 → 105 秒 | 351 → 157 秒 |
| 質の平均（MCP なし → あり） | 4.39 → 4.17 | 4.22 → 3.89 |

- **任せるとほとんど使われず、上乗せのコストだけが残る。使わせると毎回使うが、手数が増えて重くなり、質も上がらない。** Opus + Claude Code で、Kubernetes の調査を新しいセッションで 1 問ずつ頼む使い方では、どちらにしても得をしなかった。
- **はっきり効いたのは、どちらのラウンドでも T5（未使用コード）の速さだけ。** grep を何百回も回すような総当たりの調査では、グラフのクエリのほうが速い。ただし、クエリの範囲次第で取りこぼすので、結果の裏取りは必要。

## 注意点・限界

- 各条件 3 回だけ。モデルは Opus 5.5 だけ。新しいセッションでの初回の質問だけを測っている。
- 採点は LLM（Opus 5.5）が 1 回だけ。同じ A の回答でも、ラウンド 1 の採点と点が少し違う（質の平均 4.39 と 4.22）。質の比較は、同じラウンドの中でだけ行うこと。
- MCP なしのログはラウンド 1 のものを使い回している（実行日が 1 日違う）。
- CLAUDE.md を読み込ませるため、MCP ありだけ `--setting-sources project` にした。Kubernetes には `.claude/` がないので、増えるのは CLAUDE.md だけ（最初のリクエストで約 380 トークン増）。CLAUDE.md があると Kubernetes の AGENTS.md は読み込まれないことも、試し実行で確認した。
- T6-B-1 は、ログ上の開始から終了まで 29 分かかっていたが、Claude Code が記録した実行時間は 46 秒だった。待ち時間が入ったものとみて、46 秒を使っている。
- コストはサブスクリプションでの API 料金換算の参考値。
